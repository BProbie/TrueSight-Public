# 背景、创新点与不足

> 这篇文档回答「为什么做、和别人有什么不同、现在还不够好在哪里」。
> 它不替代 [ARCHITECTURE](ARCHITECTURE.md) 与 [DETECTION](DETECTION.md)，
> 而是把设计动机与取舍讲清楚。

## 一、背景：品牌仿冒为什么难防

品牌仿冒站点通常有三个特点，决定了传统方案不够用：

1. **域名变化快**：形近域名、同形异义字、换 TLD、加前后缀的成本极低，
   黑名单永远慢半拍；
2. **页面伪装好**：直接复制官方登录页，仅看域名会漏，仅看页面会被反爬；
3. **处置链条长**：发现 ≠ 取证 ≠ 举报 ≠ 下架，中间任何一步缺失都无法形成闭环。

传统做法各有短板：

| 方案 | 强项 | 短板 |
| --- | --- | --- |
| 浏览器/安全厂商黑名单 | 命中即准 | 新域名入库前的窗口期完全空白 |
| WAF / 反向代理 | 能拦已知攻击 | 不解决「用户点了外链之后」的品牌仿冒 |
| 人工举报 + 邮件下架 | 处置合法 | 慢、不可扩展、证据难固定 |
| 纯大模型研判 | 泛化好 | 成本高、结果不稳定、不可解释 |

## 二、项目的三个核心选择

### 1. 三个发现入口，一套引擎（旁路式只是其中之一）

* **外链拦截** `GET /api/v1/goto`：用户点击时实时裁决，延迟最低；
  不改被保护站点源码，只把外链改写成 `/api/v1/goto?to=...` 即可接入，
  删掉改写就恢复原样，也不接管站点全部流量；
* **周期扫描**：APScheduler 驱动形近域名生成、新域情报源与历史命中重扫，
  主动发现尚未开始传播的仿冒站；
* **人工举报**：用户 / 客服提交网址，初筛后进入人工审核队列。

三条入口共用同一 `SiteAssessor`、评分与风险分级、命中记录、证据链与处置流程。
「旁路式」描述的是外链入口的接入方式，不是项目的全部 ——
真正的价值在于三条线索最终都能进入同一条「发现 → 取证 → 处置 → 态势」闭环。

### 2. 分级降级：任何能力缺失都不阻断结论

保护等级 0–5 对应不同的能力集合；每个能力都有兜底链与熔断。
计划里出现过的能力，最终**必然**落在 `executed` 或 `skipped` 之一，
界面与任务结果都会显示「哪些没做、为什么」。

这解决了一个常见问题：演示环境没有情报源、没有模型、目标站点不可达，
系统仍然能给出「域名形近 + 证书异常」的可解释结论，而不是直接报错。

### 3. 隐私最小化：本地优先、单向脱敏投影

* 命中、证据、设置都在本机；
* 公网侧只读 `DashboardEvent` 投影表，字段只有脱敏域名与聚合信息；
* 举报者 IP 不落库，只存带盐哈希；
* 模型密钥只可写入、不可读回，日志/异常/`repr` 统一脱敏。

## 三、创新点

### 3.1 「可解释」不是一句口号：分数 = 因子之和

评分不是黑盒模型，而是分层加权：

```text
总分 = 黑名单 60 + 情报 35 + 0.40×域名 + 0.25×文本 + 0.20×证书 + 0.15×ICP
```

每个因子都带来源与中文理由，前端能逐条展示「为什么是这个分」。
唯一的策略下限（同名换 TLD）也以**补差因子**出现，而不是偷偷抬分。

### 3.2 AI 只做灰区复核，且只升不降

* 只在 35–59 分的可疑灰区调用；
* 最多 +20 分，置信度 < 0.6 不加分；
* 模型认为安全时不扣分；
* 页面文本按哈希缓存，周期重扫不重复烧额度。

页面内容是不可信输入，模型没有「洗白」高危结论的权力。
这比「让大模型直接判安全/危险」更可控、更可审计。

### 3.3 降级可见：把「没做」当成一等公民

很多系统在能力失败时静默跳过，用户以为「查过了」。
本项目把 `skipped_capabilities`、`degraded`、中文说明做成协议的一部分：

* 任务结果有 `executed` / `skipped` / `notes`；
* 判定结果有 `executed` / `skipped` / `skip_reasons`；
* 服务页能看到能力健康与熔断状态；
* 设置页对「重启后生效」的参数明确标注，不假装立即生效。

### 3.4 证据链：可自校验的本地清单

每个证据文件落盘时计算 SHA-256，清单文件本身也作为证据落盘。
任何人拿到证据目录都可以重新计算哈希，确认文件未被篡改。
它不是区块链，也不是第三方公证，但在「本地取证 + 维权附件」场景下足够实用。

### 3.5 从「发现」到「处置」的完整闭环

大多数演示只做到「发现可疑域名」。本项目把后续链路也做进同一条流水线：

* 命中去重与状态机；
* 人工确认 / 排除 / 投稿审核；
* 取证、报告、举报留痕（默认演练）；
* 脱敏态势看板与审计日志。

## 四、和常见方案的对比

| 维度 | 黑名单 | WAF | 纯 AI | TrueSight |
| --- | --- | --- | --- | --- |
| 新域名窗口期 | 差 | 差 | 中 | 中（域名层 + 内容层） |
| 品牌仿冒针对性 | 中 | 低 | 中 | 高 |
| 可解释性 | 高（命中即准） | 中 | 低 | 高（因子 + 理由） |
| 成本 | 低 | 中 | 高 | 低（本地规则 + 可选 AI） |
| 隐私 | 取决于厂商 | 中 | 低 | 高（本地优先） |
| 处置闭环 | 无 | 无 | 无 | 有（本地取证 + 留痕） |

## 五、不足与坦诚的边界

1. **阈值未大规模标定**：权重与分档来自方案推演与演示样本，真实部署需重新校准；
2. **能力覆盖不完整**：RDAP/WHOIS、DNS、视觉相似度仍是能力位；
3. **数据源依赖**：新域监控与情报需要外部 feed，仓库只带演示实现；
4. **单机架构**：SQLite + 单进程，适合单机/小团队，不适合多租户 SaaS；
5. **无自动下架**：对外举报默认演练，真实提交需人工确认（这是合规取舍）；
6. **前端 E2E 缺失**：目前靠构建 + 手工验收；
7. **打包体积**：PyInstaller onefile 约 35 MB，首次启动有解压开销；
8. **文档与界面以中文为主**：英文只保留术语与关键告警。

## 六、如果继续做，最值得做什么

| 方向 | 为什么值得 |
| --- | --- |
| 真实样本校准 + 混淆矩阵 | 直接决定误报/漏报，是生产化的前提 |
| 接入真实新域/情报源 | 把「框架」变成「能力」 |
| 视觉相似度（截图 + 感知哈希） | 补上「页面长得像」这一层证据 |
| Playwright 端到端回归 | 前端改动频繁，手工验收不可持续 |
| 证据第三方时间戳 | 提升维权附件的可信度 |
| PostgreSQL + 队列 | 多实例、更大数据量、任务重试 |

> 这些不是「画饼」，而是当前代码与真实生产之间明确存在的距离。
> 先把边界讲清楚，再谈演进，比假装什么都能做更有价值。
