# 架构说明

TrueSight 由三条发现入口（外链拦截 / 周期扫描 / 人工举报）、一套检测与评分引擎、
一条取证与处置链，以及公网 / 企业 / 平台三个前端组成。三条入口的节奏与接入方式不同，
但共用同一个 `SiteAssessor`、命中记录、证据链与处置流程。

## 一、整体结构：三端 + 一条单向脱敏通道

```
       ┌──────────────────────────┐
       │  受保护站点（品牌官网）    │   接入方式：把出站外链改写为
       │  用户点击外链 → 中转       │   /api/v1/goto?from=…&to=…
       └────────────┬─────────────┘
                    │ ① 判定（毫秒级）
                    ▼
   ┌────────────────────────────────────────────────┐
   │ 公网端（public 模式）                            │
   │  /api/v1/goto   中转裁决 + 一次性票据             │
   │  /api/v1/report 人工举报受理                     │
   │  /api/v1/dashboard 只读脱敏态势                   │
   │  静态前端：仿冒态势 / 提交举报 / 拦截提示          │
   └────────────────────────────────────────────────┘
                    ▲ ③ 单向脱敏投影（只写不读回的公开数据）
                    │
   ┌────────────────────────────────────────────────┐
   │ 本地端（local 模式）                             │
   │  检测引擎（L0/L1/L2） → 命中记录 → 处置链          │
   │  处置链：取证 → 研判报告 → 举报留痕（默认演练）      │
   │  周期任务（APScheduler，默认关闭）                 │
   │  本地管理后台 /admin（十页：总览 公告 名单 模型   │
   │                    服务 日志 设置 订阅 存储 检查） │
   │  数据：SQLite + 证据链文件（data/）                │
   └────────────────────────────────────────────────┘
```

**为什么强调「单向」**：本地端持有原始证据与完整命中信息；公网端只持有脱敏投影表
（`dashboard_events`）。即使公网端被拖库，也无法还原原始证据、WHOIS 注册人与精确 IP。

## 二、后端分层与依赖方向

```
app/
├── core/      配置 · 日志 · 错误 · 安全组件 · 分级降级   （零业务依赖，最底层）
├── utils/     URL 规范化 · 域名 · 熵 · SSRF 判定        （纯函数，无 I/O）
├── db/        ORM 模型 · 会话 · Alembic                 （只依赖 core）
├── engine/    检测引擎（纯 Python，**不依赖 FastAPI**）
│   ├── dga/          L0 域名层：生成 / 筛查 / 新域监控
│   ├── crawler/      L1 抓取层：robots + 逐跳 SSRF + 体积上限
│   ├── analyzers/    L1/L2 分析：文本语义 · TLS 证书 · ICP
│   ├── scoring/      加权评分 · 风险分级 · 意图分类
│   ├── reporting/    研判报告（大模型优先、规则模板兜底）
│   ├── forensics/    证据链固定（原文 + SHA-256 + 时间戳 + 清单）
│   └── contracts.py  对外唯一契约：SiteAssessor 协议与 SiteAssessment
├── llm/       供应商适配（OpenAI 兼容）+ 注册表 + 从库装配
├── scheduler/ 任务编排（runner）与调度接线（service）
├── services/  业务服务：名单 · 判定 · 举报 · 处置 · 取证 · 后台 · 设置存储
├── schemas/   Pydantic 请求模型（外部输入的校验边界）
├── api/       路由装配（public 一组 / local 一组）
├── web.py     前端静态产物挂载
└── context.py 依赖容器（把上面这些装配成一个可注入对象）
```

依赖方向：**上层可依赖下层，下层绝不反向依赖**。两条硬约束由代码结构保证：

1. `engine/` 不认识 FastAPI，也不认识 SQLAlchemy —— 因此它可以脱离 Web 与数据库单测
   （`tests/engine/` 全部离线跑）；
2. 调用方只依赖 `engine.contracts.SiteAssessor` 这一个协议 —— 引擎换实现、加能力，
   `goto` / `report` / 后台扫描的代码一行都不用改。

## 三、一次判定的完整时序（`/api/v1/goto`）

下面以外链拦截为例。周期扫描与人工举报复用同一评估器与评分环节，
差别只在入口、限流与触发节奏；命中之后同样进入取证与处置链。

```
用户点击外链
   │
   ├─① 参数与安全裁决：normalize_url（拒绝控制字符/反斜杠/userinfo）
   │                 → SsrfGuard（协议白名单、端口白名单、私网与元数据黑名单、DNS 解析后校验）
   │
   ├─② 名单快路径（内存快照，TTL 60s）：
   │     受保护资产 / 白名单 → SAFE（直接 302）
   │     黑名单 → DANGEROUS（score=90）
   │
   ├─③ 评估引擎（受 2500ms 时间预算约束）
   │     L0 域名筛查（纯本地计算）
   │     → 威胁情报（可插拔，未配置即跳过）
   │     → L1 合规抓取 → 文本语义（依赖抓取结果）
   │     → TLS 证书 + ICP 备案
   │     → 加权评分 → 结论 / 风险等级 / 意图
   │
   ├─④ 按「风险等级 + 保护等级」决定动作：
   │     0 不处理 · 1 仅高危提示 · 2-4 中等及以上确认（2/3/4 级分别 1/2/3 次）
   │     · 5 级中等及以上直接拦截
   │
   └─⑤ 出具一次性票据（HMAC 签名，默认 300s）：
        放行 → 302 到目标；需确认 → 302 到 /gate?ticket=…；拦截 → 拒绝跳转
```

三条边界条件（都有测试守着）：

* **超时** → `INDETERMINATE`，按保护等级走兜底动作，绝不让用户卡住；
* **单能力失败** → 只记 `skipped_capabilities` + 一条中文说明，判定继续；
* **名单数据本身读不到** → 唯一返回 `INDETERMINATE` 的情形（没有最低限度依据）。

## 四、命中之后：处置链

```
命中记录（findings）
   │  finding 落库后**才**进入处置，处置在 goto 热路径之外
   ├─① 取证：重新抓一次页面（评估结论刻意不含原文，隐私面最小）
   │       → HTML / 文本 / 证书 / 证据清单（data/evidence/<指纹>/）
   │       → 库中只写索引行（相对路径 + SHA-256 + 采集上下文）
   ├─② 研判报告：大模型优先 → 失败或未配置则规则模板兜底（**报告永远生得出来**）
   │       页面原文以显式定界符隔离，且报告**绝不回流判定**
   └─③ 举报留痕：默认 dry_run（只生成、不发送）
           人工确认后才走真实通道；失败只记 failed + 留痕，不抛错
```

**为什么处置不塞进判定里**：一次模型调用要十几秒，塞进用户的点击路径等于把正常跳转
拖成超时。判定要快，处置要全，两者用 `SiteAssessment` 与 `Finding` 解耦。

## 五、可观测性：降级必须可见

贯穿全项目的一条原则：**「少做了一步」必须能被看见**。

| 位置 | 机制 |
| --- | --- |
| 评估引擎 | 计划内能力必然落在 `executed_capabilities` ∪ `skipped_capabilities`（`_settle_plan`，有测试钉死） |
| 抓取与证书 | 「查不到」≠「不合规」：握手失败只报不可达，不产出伪造证书结论 |
| 后台任务 | 每个 `TaskKind` 要么执行、要么有明确跳过原因；记录 `executed/skipped/notes` |
| 处置链 | 每步失败记 `skipped` + 中文说明；报告是否走了模板可查（`provider` 字段） |
| 举报通道 | 未启用开关 → 明确报错；未配置真实通道 → 只演练并写明原因 |
| 管理后台 | 「服务」页展示每个能力的实时状态（可用 / 降级 / 已熔断 + 连续失败次数） |

## 六、并发、资源与故障隔离

| 关注点 | 做法 |
| --- | --- |
| 阻塞 I/O | 抓取走 httpx 异步；TLS 握手走线程池；数据库走短事务（`session_scope`） |
| 超时 | 判定 2500ms（可配）；单任务 900s（可配）；模型调用默认 120s（可配） |
| 熔断 | 连续失败 3 次置为不可用，冷却后半开探测；**目标站点失败不计入熔断**（否则几个打不开的网站就能吃掉抓取能力） |
| 取消传播 | 任何兜底链都先 `except CancelledError: raise` —— 吞掉取消会让上层超时形同虚设 |
| 外部依赖 | 全部经协议注入（fetcher / tls / icp / intel / feed / llm 客户端工厂），可在测试与离线环境整体替换 |
| 资源释放 | `AppContext.aclose()` 统一回收 HTTP 客户端、调度器与新替换的 LLM 注册表 |
| 限流 | 令牌桶（IP+UA+路径派生指纹做键，不落明文 IP），高等级叠加人机验证与可疑延迟 |

## 七、前后端协作

```
frontend/
├── packages/shared/      API 客户端 · 类型契约（与后端视图字段一一对应）·
│                         中文标签映射 · 字节/时间格式化
├── apps/web-client/      公网侧：仿冒态势 / 提交举报 / 拦截提示
└── apps/admin-console/   本地管理后台：十页（总览 / 公告 / 名单 / 模型 / 服务 / 日志 / 设置 / 订阅 / 存储 / 检查）
```

约定：

* 前端只通过 `/api/v1/*` 交互，**不做任何业务判断**（判定、评分、状态机全在后端）；
* 管理后台接口只在 `local` 模式挂载，`public` 模式下连路由都不存在（不是靠开关遮挡）；
* 报告正文含模型生成文本，前端一律按纯文本/受控 Markdown 渲染，**禁止 `v-html`**；
* 构建产物由后端挂载（`/` 与 `/admin`），缺产物不影响接口 —— 页面是可选装饰。
