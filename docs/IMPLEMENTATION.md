## 二、一次请求的完整旅程

### 2.1 外链拦截：最低延迟的旁路

```
浏览器点击外链
  → /api/v1/goto?to=...
    → URL 规范化（大小写、端口、IDN、尾点）
    → SSRF 逐跳校验（首跳 + 每次重定向）
    → 白名单/黑名单/受保护资产快速命中
    → 按保护等级决定是否进入 2 级判定（robots → 抓页 → TLS → 可选 AI）
    → 评分与风险等级
    → 安全则 302 放行；可疑则确认页；高危则拦截页
```

关键点：

* **不修改被保护站点源码**：接入方只需要把外链换成 `/api/v1/goto?to=...`，随时可以摘除；
* **判定有时间预算**（`goto.decision_timeout_ms`）：预算耗尽不是「放行」，而是明确降级为
  「无法判定」并留下中文说明；
* **每一跳都重新做 SSRF 校验**：只校验首跳会被「公网 URL 302 到内网」绕过。

对应实现：`app/services/goto.py`、`app/engine/crawler/fetcher.py`、`app/utils/ssrf.py`。

### 2.2 周期扫描：主动发现

```
调度器（默认关闭）
  → 形近域名生成 → 候选筛查（DNS/情报源/新域监控）
  → 逐个评估（与 goto 共用同一个评估器）
  → 命中落库 → 取证 → 报告 → 举报留痕（dry-run）
```

扫描与 goto 共用同一套 `SiteAssessor`。这不是为了省代码，而是为了保证
「同一个域名从哪条入口进来，结论一致」。差异只在触发方式与限流参数。

对应实现：`app/scheduler/`、`app/engine/pipeline.py`、`app/services/disposition.py`。

### 2.3 人工举报：外部线索

```
POST /api/v1/report
  → 人机验证票据（可选常驻票据）
  → 受保护资产/白名单直接拒绝（不能举报自己）
  → 入库为待审核举报 → 后台初筛 → 关联命中或新建命中
```

举报人 IP 只存带盐哈希，正文做长度限制；公网端永远拿不到原始证据。

### 2.4 请求进入后端后的公共链路

```
FastAPI 中间件
  → 安全响应头 / 客户端指纹（只在受信代理后采信 XFF）
  → 会话解析（B 端 ts_session / A 端 ts_root_session）
  → CSRF（写操作）
  → 路由依赖注入（ContextDep → AppContext）
  → 业务服务
  → 统一错误处理（TrueSightError → {error:{code,message,detail?}}）
  → log_event 结构化日志
```

`AppContext` 是进程级依赖容器（`app/context.py`）：数据库、安全组件、评估器、套餐、
账号、测试模式等都在这里装配，路由只依赖上下文。这样测试可以替换任一组件，而不必
monkeypatch 全局变量。

## 三、分层与目录（为什么这样分）

| 层 | 目录 | 职责 | 不该做什么 |
| --- | --- | --- | --- |
| 接口 | `app/api/` | 参数校验、鉴权、把结果拼成响应 | 不写业务规则、不直接操作 ORM 细节 |
| 服务 | `app/services/` | 业务规则、事务边界、权限判断 | 不解析 HTTP、不构造响应 |
| 引擎 | `app/engine/` | 纯检测能力（抓取、证书、评分、报告） | 不知道租户、登录、页面 |
| 数据 | `app/db/` | 模型、会话、枚举 | 不含业务分支 |
| 核心 | `app/core/` | 配置、错误、日志、降级、安全 | 不依赖具体业务服务 |

为什么把引擎独立出来：检测能力需要**可离线测试**。引擎只接受注入的 fetcher / TLS /
ICP / LLM，测试用假实现即可跑完整条链路，不访问真实网络（`AGENTS.md` 铁律 2）。

前端同样是三层：`frontend/apps/*`（三个入口）、`frontend/packages/shared`（API 客户端、
主题、头像、验证码 hook）。共享层只放「三端行为必须一致」的东西，页面差异留在各 app。

## 四、十个关键设计决定

这一节只写**为什么**，具体实现放在第五节。

### 4.1 为什么订阅是否生效完全由时间判定

如果给订阅加一个 `status=active/expired` 字段，就需要定时任务翻转状态；进程停摆、
任务失败或时钟异常都会出现「已过期还可用」或「未到期却失效」。因此：

* 生效条件 = `starts_at <= now < expires_at` 且 `cancelled_at is None`；
* 没有定时任务参与权益判定；重启、宕机、改系统时间都不会让结论漂移；
* 代价：每次解析权益都要比较时间，且历史记录必须完整保留（不能物理删除）。

### 4.2 为什么同套餐续费要复用原记录

早期实现把「续费」当成「取消旧订阅 + 新建一条从旧到期时间开始的订阅」。这在单次
续费时看起来正确，但连续点两次「开通 30 天」会出现：

```
第一次：A: [now, now+30d)
第二次：A 被取消；B: [now+30d, now+60d)  ← 当前时刻没有任何生效订阅
```

页面于是错误显示「免费版」。修复方式是：同套餐续费直接延长原记录的 `expires_at`，
只有切换套餐才取消旧记录。这个 bug 的回归测试在
`tests/services/test_plans.py::test_renewing_same_plan_twice_keeps_plan_and_extends_expiry`。

### 4.3 为什么套餐权益要版本化

直接改 `plans` 行会让历史订单被追溯改写：昨天买的 100 资产套餐，今天变成 50，
用户无法解释。`plan_versions` 用 `effective_from` 保存不可变快照：

* 当前权益 = 已生效的最新版本；
* 未来版本不提前出现在 B 端；
* A 端可以预约调价/调配额，到点自然生效，不需要定时任务；
* 历史版本保留，可回答「当时卖的是什么」。

### 4.4 为什么升级抵扣按「剩余计费月」而不是按天折算

按天折算会产生大量小数金额与舍入争议；方案要求只做展示报价，不接支付。因此规则是：

```
应付 = 新套餐月价 × 购买月数
     − 旧套餐月价 × min(旧套餐剩余计费月数, 购买月数)
```

* 计费月固定 30 天（720 小时）；
* 剩余时间**向上取整**：刚买 60 天、过了几秒仍算 2 个月，否则用户会觉得「刚买完就少
  抵扣一个月」；
* 抵扣不超过本次购买月数，应付金额不会为负；
* 同套餐续费与降级不抵扣。

实现：`EntitlementService.quote_upgrade`；接口：`GET /api/v1/admin/subscription/quote`。
前端只展示，不参与定价——价格只有一个权威来源。

### 4.5 为什么要有「测试模式」而不是只靠环境变量

演示环境需要「免费开通 VIP、任意验证码通过、注册送 SVIP」，正式交付则必须拒绝这些。
如果只靠 `.env`，部署时很容易忘记切换，而且切换过程不可见。测试模式做成：

* 库内持久化（`settings` 表的 `platform.test_mode*`），A 端可见、可审计、重启恢复；
* 「默认值」与「当前值」分离：改默认值不会覆盖运营人员已经做出的正式/测试决定；
* 测试模式关闭后，收紧的是**行为**而不是界面文案：B 端自助开通/降级直接 403，
  验证码强制 strict，注册不再赠送测试权益。

### 4.6 为什么错误只在边界归一化

第三方库的异常（httpx、SQLAlchemy、Pydantic）如果泄漏到上层，调用方无法稳定判断
「是没找到、还是冲突、还是上游失败」。因此：

* 外部异常在边界转成 `app/core/errors.py` 里的项目错误；
* API 统一返回 `{error:{code,message,detail?}}`；
* `InputError` / `ConflictError` / `FeatureDisabledError` 的 `message` 直接展示业务原因
  （如「邮箱已被绑定」「正式服务请联系平台运营」），其余错误默认只返回公共文案，
  防止内部细节外泄；
* 上层不得直接 `except httpx...`。

### 4.7 为什么降级必须可见

检测链里任何一项能力（抓页、TLS、ICP、AI、情报源）都可能不可用。项目选择**继续给结论**，
但必须把「哪一步没做」写进 `skipped_capabilities` 或中文说明。禁止静默少做一步：
用户看到 0 分，必须能知道「不是安全，而是没查」。

### 4.8 为什么公网只消费脱敏投影

公网看板不直接查原始命中表，而是查 `dashboard` 投影：域名、风险等级、时间、聚合统计，
不含证据路径、举报人信息、内部备注。这样即使公网页面被攻破，也拿不到原始数据。

### 4.9 为什么 B 端与 A 端账号空间隔离

企业账号与平台账号使用不同的租户、Cookie 名称与 Cookie Path（`/root`）。即使同一个
浏览器同时登录两端，企业接口也读不到平台会话，反之亦然。登录解析也按端隔离：
企业登录页不会命中平台账号，平台登录只在 `platform` 租户内解析。

### 4.10 为什么接受「单进程」这个前提

SQLite + 进程内锁 + 进程内设置缓存，让单机部署足够简单可靠。代价是：

* 配额校验的锁只在单进程有效；
* A 端切换测试模式只在当前进程立即生效；
* 多实例部署需要数据库行锁/唯一约束与配置广播。

代码与文档都明确写出这个边界，而不是假装多实例也安全（见
[STATUS](STATUS.md#五看得见与看不见的边界)）。

## 五、关键实现细节

### 5.1 订阅、续费与升级抵扣

核心方法（`app/services/plans.py`）：

| 方法 | 作用 | 关键约束 |
| --- | --- | --- |
| `subscribe` | 开通/续期/切换套餐 | 同套餐延长原记录；切换则取消其他套餐 |
| `quote_upgrade` | 计算原价、抵扣、应付 | 只升不降；抵扣月数取 min |
| `cancel_subscription` | 立即取消 | 回落到租户默认套餐/免费版 |
| `entitlements` | 解析当前权益 | 覆盖 > 订阅 > 租户默认 > 免费 |

几个容易忽略的点：

* `subscribe` 会兼容旧数据中「未来才开始」的同套餐记录，把 `starts_at` 拉回 `now`，
  避免升级后仍有一段无权益空档；
* 判断「同套餐」时同时要求 `cancelled_at is None` 且 `expires_at > now`，过期记录不会
  被错误复用；
* 抵扣报价使用的是**当前生效订阅**的月价与到期时间，不是租户默认套餐；
* 免费计划月价为 0，升级抵扣为 0，页面显示「免费」。

正式服务下，B 端接口在进入服务层之前就拒绝（`app/api/local/subscription.py`）：
没有支付与对账流程时允许调用，等于允许免费获得 VIP。A 端平台接口不受影响，
用于线下合同开通。

### 5.2 服务形态开关（测试模式）

模块：`app/services/test_mode.py`。

```
settings 表
  platform.test_mode          ← 当前模式的显式值（可缺省）
  platform.test_mode_default  ← 默认值（可缺省，内置默认 true）
```

解析规则：

```
enabled = 显式值（存在时） else 默认值
source  = "explicit" | "default"
```

* `load()` 在 lifespan 建表后调用，从库里恢复；坏值只告警并回退默认值；
* `update()` 写库并同步进程内缓存，A 端切换后当前进程立即生效；
* `is_enabled()` 读缓存，避免验证码校验路径频繁查库。

生效点：

| 位置 | 行为 |
| --- | --- |
| `api/local/subscription.py` | 正式服务拒绝自助开通/续期/取消 |
| `services/verification.py` | 正式服务强制 strict，即使配置是 stub |
| `api/local/auth.py` | 正式服务注册不赠送 365 天 SVIP |
| `frontend/apps/admin-console` 订阅页 | 禁用按钮并展示「联系平台运营」 |
| `frontend/apps/root-console` 设置页 | 展示来源、实际验证码模式与风险告警 |

### 5.3 验证码：stub、strict 与强制 strict

`VerificationService` 只负责「生成、存储、过期、校验、频率限制」，发送渠道通过
`sender` 回调注入。两种模式：

* `stub`：目标格式合法即通过，不发信、不回显验证码；界面必须明确提示「任意验证码可用」；
* `strict`：比对 SHA-256 哈希、有效期与尝试次数，一次性消费，防重放。

共享前端组件 `useVerificationCodes` 会根据返回的 `mode` 与 `delivered` 显示三种提示：
演示模式（不会真正发送）、strict 已送达、strict 未送达（请联系管理员检查渠道）。
不能把「没发出去」统一显示成「已发送」，否则用户会一直空等。

测试模式关闭时，`stub` 属性直接返回 `False`，即**配置仍是 stub 也按 strict 运行**。
这不是为了「偷偷改配置」，而是为了让正式服务不会因为漏改环境变量而放行空验证码。

代价必须说清：如果部署没有真实发送渠道，强制 strict 会让注册/找回无法完成。
A 端设置页在「正式服务 + 配置 stub」时给出醒目告警，运维必须先接渠道再关闭测试模式。

### 5.4 登录、会话与 CSRF

* 密码使用 scrypt 哈希；错误提示不区分「用户不存在」与「密码错误」；
* 连续失败按账号+客户端指纹锁定（默认 5 次 / 15 分钟）；
* 会话 Cookie `HttpOnly` + `SameSite=Lax`，B 端 `ts_session`，A 端 `ts_root_session`
  且 `Path=/root`；
* 写操作要求 CSRF 双提交；非 `/admin` 前缀的接口显式依赖 `CsrfDep`；
* 默认单设备在线，换设备登录踢掉旧会话；A 端可按租户调整上限。

### 5.5 检测引擎与降级

`EngineAssessor` 是唯一评估出口（`app/engine/pipeline.py`）。它按保护等级决定投入哪些
能力，并保证每个计划内能力都结算为 `executed` 或 `skipped`：

* 抓取失败 → 记录原因，继续用现有信息评分；
* TLS/ICP 不可用 → 明确「未做」，不伪造结论；
* AI 只在灰区（35–59 分）调用，超时或未配置 → 跳过并说明；
* 评分只升不降：确认过的结论不会因为一次重扫失败而变弱；
* 新域监控的行业词表不是「只认金融」：默认覆盖电商、通信、医疗、教育等行业，
  部署方可以追加自己的行业词（`sector_keywords`）。

### 5.6 处置、证据与报告

* 证据文件与数据库分离，只存路径 + SHA-256 + 脱敏上下文；
* 证据清单可自校验，避免「文件被替换但记录仍显示完整」；
* 报告优先生成大模型版本，失败时回退模板，并在结果里标注使用了哪种；
* 处置默认 `dry_run`，举报留痕只记录「打算发给谁」，不会自动对外发送。

### 5.7 前端三端与共享契约

* `web-client`：公网态势、举报、拦截提示；没有管理接口；
* `admin-console`：B 端管理后台；登录、注册、找回密码共用一张卡片的分段标签，
  首次部署没有账号时默认落到「注册」，不再提供初始化入口；
* `root-console`：A 端平台控制台；独立登录、独立 Cookie、设置页维护服务形态；
* `packages/shared`：`ApiClient`（错误信封解析、CSRF 注入）、主题、头像、验证码 hook。

公告横幅不是「把接口返回的公告全画出来」，而是一个小型提示队列：未读 ID 存浏览器本地，
新公告逐条进入队列，每条 15 秒自动消失，点 × 立即关闭；横幅限高、标题单行、正文两行，
避免公告把首屏业务内容挤走。已读记录只保留最近 200 条，防止本地存储无限增长。

两个容易踩的前端约束：

* 不用 `v-html` 渲染后端或模型生成的文本（提示词注入会升级为 XSS）；
* 设置页不参与 `KeepAlive` 缓存，否则未保存的草稿会跨菜单残留。

## 六、踩坑与修复记录

| 现象 | 根因 | 修复 | 回归测试 |
| --- | --- | --- | --- |
| 连续两次开通同套餐后显示免费版 | 旧订阅被取消、新订阅未来才开始，当前时刻无生效订阅 | 同套餐续费复用原记录并延长 `expires_at` | `test_renewing_same_plan_twice_keeps_plan_and_extends_expiry` |
| 刚买 60 天 VIP，升级报价只抵扣 1 个月 | 剩余 59.999 天被 `floor` 成 1 | 改为向上取整 | `test_upgrade_quote_credits_remaining_months` |
| 注册/登录只显示「请求参数不合法」 | 所有 `InputError` 都走公共文案 | 业务错误设 `expose_message=True`，字段校验输出中文 | `test_registration_errors_are_specific` |
| 切换登录/注册时上一屏错误残留 | 错误状态没有随标签清理 | `switchAuth` 清空 `error/notice` | 前端交互验收 |
| 设置页未保存的草稿跨菜单残留 | 设置页被 `KeepAlive` 缓存 | `App.vue` 的 `exclude` 保留 `SettingsView` | 前端构建 + 人工验收 |
| 伪造 `X-Forwarded-For` 可绕过限流 | 无条件采信转发头 | 只有配置 `abuse.trusted_proxies` 才解析 | `tests/utils/test_net.py` |
| Windows PowerShell 脚本中文乱码/语法错 | `.ps1` 去掉 BOM 后被按 ANSI 解码 | 所有 `.ps1` 保留 UTF-8 BOM | 脚本启动验收 |
| `vite build` 报 JSON 解析错误 | `*.json` 被加了 UTF-8 BOM | JSON 一律无 BOM | 前端构建门禁 |
| 验证码明文出现在日志/响应 | 调试时顺手打印 | 日志只记脱敏目标；验证码不可读回 | 架构 AST 测试 + 代码评审 |
| 公告横幅堆叠、无法关闭、长文占满首屏 | 直接渲染接口返回的全部公告 | 未读队列 + 每条 15 秒自动消失 + × 手动关闭 + 标题单行/正文两行限高 | 前端交互验收 |
| 「验证码已发送」但用户没收到 | `stub` 不真正发送；strict 缺发送渠道时 `delivered=false` | 共享组件按 `mode`/`delivered` 分三种提示：演示模式/已送达/未能发送；正式服务强制 strict 并告警 | `test_formal_service_forces_strict_even_if_configured_stub` |
| 拦截确认页提交失败后按钮「点了没反应」 | 确认次数已点满，事件处理直接返回，没有再次提交 | 次数已满时再次点击直接重试，不再要求用户回到原链接 | 前端构建 + 手工验收 |
| 企业构建下词典文件导入返回 401/403 | 上传走原生 `fetch`，`credentials: 'omit'` 且未带 CSRF 头 | 改为 `same-origin` 凭据并附带 `X-CSRF-Token`；401 时通知外壳重新登录 | 前端构建 + 企业模式验收 |

## 七、调试与验收手册

### 7.1 离线复现一条检测结论

```powershell
cd server
.\.venv\Scripts\python.exe -m pytest tests/engine -q
```

引擎测试注入假 fetcher / 假 TLS / 假 ICP / 假 LLM，不访问网络；时间相关用例注入可控时钟。

### 7.2 看一次判定为什么是这个分数

1. 管理后台「日志」页打开命中详情，查看 `reasons`、`skipped_capabilities` 与评分明细；
2. 如果启用了 AI，详情里会标明「AI 复核」是否执行、模型与耗时；
3. 若结论是「无法判定」，先看降级说明，再看 `goto.decision_timeout_ms` 是否过小。

### 7.3 订阅相关问题排查顺序

1. `GET /api/v1/admin/subscription` 看 `entitlements.source`（subscription / tenant / default）；
2. 看 `history` 里是否有 `cancelled_at` 非空但仍在生效窗口内的记录；
3. 看 `test_mode.enabled`：正式服务下自助开通会被拒绝；
4. 升级金额不对时，先确认剩余天数与 `BILLING_MONTH_HOURS=720` 的取整规则。

### 7.4 前端验收

```powershell
cd frontend
npm run build
```

三个 app 都会产出 `dist`，由后端挂载。验收重点：

* `/admin/` 首次部署默认「注册」标签，登录/注册/找回在同一张卡片内切换；
* `/admin/` 公告横幅只展示未读公告、逐条自动消失，且限高不挤占首屏；
* `/admin/` 订阅页切换 30/90/365 天价格联动，正式服务下按钮禁用；
* `/root/` 设置页两个开关独立生效，来源与验证码模式展示正确。

## 九、明确没做与已知边界

* 不接支付/发票/退款：正式服务由平台运营线下开通；
* 多实例：配额锁、测试模式缓存、调度器都是单进程假设；
* 真实邮件/短信：需要部署方注入发送渠道；
* 检测数据未全量租户隔离：账号、订阅、公告已隔离，命中数据仍是共享表；
* 第三方时间戳/公证、自动对外举报：当前只做本地证据与 dry-run 留痕。

这些不是「忘了做」，而是方案里明确的分级边界。判断标准见
[STATUS](STATUS.md) 与 [FAQ](FAQ.md#六哪些是明确降级而不是没做)。
